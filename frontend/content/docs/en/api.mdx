The ClickFix REST API lets you open conversations, add messages and internal notes, keep contact and company data in sync, send customer-health signals and subscribe to events with webhooks. This page explains the rules shared by every endpoint. Endpoints, schemas and ready-made requests for every language are in the [API reference](/docs/api-reference?lang=en); the end-to-end setup order is the [Integration guide](/docs/integration-guide?lang=en); the packages are on [SDKs](/docs/integration-guide/sdks?lang=en). The reference contains only public, stable endpoints; the panel's own internal endpoints cannot be called with an API key.

**Base URL:** `https://api.getclickfix.com/v1/public-api`

## 1. Create an API key [#create-api-key]

1. Open **Organization → API and automations**. You need permission to manage API keys in the organization to see the page.
2. On the **API keys** tab press **New API key** and give the key a name that identifies the integration (e.g. "ERP sync").
3. Pick only the **scopes** the integration needs; optionally set a **requests per minute** limit (1–6000, default 120) and an **expiry** date.
4. Press **Create key** and copy the key right away. It starts with `cf_sk_` and is shown **only once**; ClickFix keeps only a digest.

**Revoke** on the same page invalidates a key immediately. If a key leaked, revoke it first, then create a new one.

> API keys are used on the server only. Never put them in browser code, a mobile app or a public repository. Mobile apps use an [app key](/docs/integration-guide/mobile?lang=en#mobile-session); websites use [`user_hash`](/docs/integration-guide/identity?lang=en).

### What a key can reach [#key-access]

- A key is bound to the **organization** it was created in; no `X-Organization` style header is needed.
- A key is limited to the **current** permissions of the member who created it. If that member loses permissions, is deactivated or leaves the organization, the key is restricted or stops working accordingly.
- A request passes only when the key has the relevant **scope** and the member has the relevant **permission**.

### Scopes [#scopes]

| Scope                 | Allows                                                              |
| --------------------- | ------------------------------------------------------------------- |
| `conversations:read`  | Reading conversations and messages                                  |
| `conversations:write` | Creating and updating conversations, adding messages and notes      |
| `contacts:read`       | Reading contacts                                                    |
| `contacts:write`      | Creating contacts, upserting by external id and updating contacts   |
| `companies:read`      | Reading companies                                                   |
| `triggers:read`       | Polling trigger events                                              |
| `webhooks:read`       | Reading webhook subscriptions                                       |
| `webhooks:write`      | Creating, updating and deleting webhook and REST hook subscriptions |
| `revenue:write`       | Sending company revenue                                             |
| `health:write`        | Sending the customer-health usage signal (0–100)                    |
| `events:write`        | Sending product events to the company timeline                      |

The scope each endpoint needs is stated in its reference description. A missing scope returns `403 FORBIDDEN` and names the scope in the message.

## 2. Your first request [#first-request]

Send the key as a `Bearer` token in the `Authorization` header on every request. Your first request in five minutes: put the key in an environment variable on your server and list contacts.

```bash
export CLICKFIX_API_KEY="cf_sk_..."

curl "https://api.getclickfix.com/v1/public-api/contacts?limit=5" \
  -H "Authorization: Bearer $CLICKFIX_API_KEY"
```

Then pick a contact and a channel (`inbox_uuid`) and open a conversation. The contact is given as `contact_uuid` or, with the id from your own system, as `contact_external_id`. Writes require `Idempotency-Key`:

```bash
curl -X POST "https://api.getclickfix.com/v1/public-api/conversations" \
  -H "Authorization: Bearer $CLICKFIX_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: order-1042-support" \
  -d '{
    "contact_external_id": "1001",
    "inbox_uuid": "CHANNEL_UUID",
    "subject": "Delivery question"
  }'
```

The response is `201` with the conversation id in `data.uuid`. Sending the same request with the same `Idempotency-Key` again does not open a second conversation; the first response is returned as is. `inbox_uuid` is the id of one of your active channels; contact and channel must belong to the key's organization. The conversation is assigned to the member who created the key; on a web widget channel the user sees it in the widget once they sign in on your site with `identify`.

Send `private: true` to add an internal note (never delivered to the customer):

```bash
curl -X POST "https://api.getclickfix.com/v1/public-api/conversations/CONVERSATION_UUID/messages" \
  -H "Authorization: Bearer $CLICKFIX_API_KEY" \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: 6f1c0e3a-note-1" \
  -d '{ "content": "The order has shipped.", "private": true, "client_id": "6f1c0e3a-0d0b-4a4e-9a51-3c8b7d2f1e90" }'
```

## Response envelope [#response-format]

Every response uses the same envelope. A successful response:

```json
{
  "success": true,
  "data": { "uuid": "8f0e…", "status": "open" },
  "meta": { "request_id": "01JB…" }
}
```

An error response:

```json
{
  "success": false,
  "error": {
    "code": "VALIDATION_ERROR",
    "message": "Invalid input; writes require Idempotency-Key",
    "details": [{ "field": "subject", "message": "too long", "code": "max" }]
  },
  "meta": { "request_id": "01JB…" }
}
```

Handle errors by `error.code`; the `message` text is informational and may change. Share `meta.request_id` when contacting support; we find the request by it.

## Error codes [#errors]

| HTTP | `error.code`                                                            | When                                                                                            | What to do                                                                           |
| ---- | ----------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| 400  | `VALIDATION_ERROR`                                                      | The body is invalid, a field rule is violated or a write lacks `Idempotency-Key`                | Read `details`, fix the request; do not retry the same request                       |
| 401  | `UNAUTHENTICATED`                                                       | The key is missing, wrong, revoked or expired                                                   | Check the key, create a new one if needed                                            |
| 403  | `FORBIDDEN`                                                             | The key's scope or the creating member's permission is not enough                               | Add the scope (new key) or update the member's role                                  |
| 403  | `ENTITLEMENT_REQUIRED`, `PLAN_LIMIT_EXCEEDED`, `SUBSCRIPTION_READ_ONLY` | The organization's plan lacks the feature, a quota is full or the subscription is read-only     | Review the plan with your organization admin                                         |
| 404  | `NOT_FOUND`                                                             | The record does not exist, belongs to another organization or the endpoint is not public        | Check the id and the path                                                            |
| 409  | `IDEMPOTENCY_CONFLICT`                                                  | The same `Idempotency-Key` was used with a different request, or the first one is still running | Generate a new key for a new action; retry the running one with the same key shortly |
| 409  | `EXTERNAL_ID_EXISTS`                                                    | The external id belongs to another contact                                                      | See the [external id](/docs/integration-guide/contacts-companies?lang=en) rules      |
| 410  | `CURSOR_EXPIRED`                                                        | The trigger cursor is no longer valid                                                           | Re-read the resources and start again with `cursor=0`                                |
| 429  | `RATE_LIMITED`                                                          | The key's per-minute limit was exceeded                                                         | Wait `Retry-After` seconds and retry                                                 |
| 502  | `RESULT_TOO_LARGE`                                                      | The response is too large                                                                       | Lower `limit` or add a filter                                                        |
| 500  | `INTERNAL_ERROR`                                                        | Unexpected server error                                                                         | Retry with exponential backoff; if it persists, contact us with the `request_id`     |

## Pagination [#pagination]

List endpoints accept `limit` (default 20, at most 100) and `offset` and return one structure:

```json
{
  "success": true,
  "data": { "items": [], "total": 134, "limit": 20, "offset": 40 }
}
```

For the next page increase `offset` by `limit`; stop when `items` is empty or `offset + limit >= total`. The contact list also supports `q` for search and `external_id` for an exact match. Pagination is for snapshots; to keep many records in sync use [webhooks](/docs/webhooks?lang=en) or [trigger polling](/docs/mcp-integrations?lang=en) (`GET /triggers`, cursor based) instead of polling page by page.

## Writes and Idempotency-Key [#idempotency]

Every request other than `GET` **requires** the `Idempotency-Key` header (at most 200 bytes).

- Generate a unique value per logical action, e.g. `order-1042-refund` or a UUID.
- On a network error or timeout send the same request again **with the same key and the same body**. ClickFix stores the first completed response and returns it as is; the action is not performed twice.
- Keys are kept for 24 hours. Using the same key with a different body, method or path returns `409 IDEMPOTENCY_CONFLICT`.
- If the stored response is an error (e.g. `400`), retrying with the same key returns the same error. Use a new key once you fixed the input.
- When sending messages, `client_id` adds another layer of duplicate protection.

## Rate limits and sizes [#rate-limits]

- Every API key has a per-minute request limit: **120** by default, 1–6000 when creating the key.
- Over the limit the API returns `429 RATE_LIMITED` with a `Retry-After` header (seconds). Wait that long, then retry with exponential backoff and jitter.
- Use a separate key per integration; the limit applies per key.
- Request bodies are at most **128 KB**.
- Do not retry `400`, `401`, `403` and `404`; fix the request first.

## Versioning [#versioning]

- The API version is in the path: `/v1/...`. Within `v1` only **backwards-compatible** changes are made: new endpoints, new optional fields, new event types, new error codes.
- Your client must ignore response fields and event types it does not know.
- Breaking changes such as removing a field, changing its meaning or adding a required field come only with a new major version (`/v2`) and are announced ahead; the old version keeps working during the transition.
- Endpoints not in the reference are not part of the public API and may change without notice.

## Endpoints [#endpoints]

| Action                                    | Endpoint                                                     | Scope                                                      |
| ----------------------------------------- | ------------------------------------------------------------ | ---------------------------------------------------------- |
| List conversations                        | `GET /conversations`                                         | `conversations:read`                                       |
| Create a conversation                     | `POST /conversations`                                        | `conversations:write`                                      |
| Get / update a conversation               | `GET` / `PATCH /conversations/{uuid}`                        | `conversations:read` / `conversations:write`               |
| List messages / add a message or note     | `GET` / `POST /conversations/{uuid}/messages`                | `conversations:read` / `conversations:write`               |
| List contacts                             | `GET /contacts`                                              | `contacts:read`                                            |
| Create a contact                          | `POST /contacts`                                             | `contacts:write`                                           |
| Create or update a contact by external id | `PUT /contacts/by-external-id`                               | `contacts:write`                                           |
| Update a contact                          | `PATCH /contacts/{uuid}`                                     | `contacts:write`                                           |
| List companies                            | `GET /companies`                                             | `companies:read`                                           |
| Company revenue                           | `PUT /company-revenue`                                       | `revenue:write`                                            |
| Company usage signal (0-100)              | `PUT /company-usage`                                         | `health:write`                                             |
| Company event                             | `POST /company-events`                                       | `events:write`                                             |
| Webhook subscriptions                     | `GET` / `POST /webhooks`, `PUT` / `DELETE /webhooks/{uuid}`  | `webhooks:read` / `webhooks:write`                         |
| Poll triggers                             | `GET /triggers`                                              | `triggers:read`                                            |
| REST hook subscribe / unsubscribe         | `POST /subscriptions`, `DELETE /subscriptions/{uuid}`        | `webhooks:write`                                           |
| Customer message to the API channel       | `POST /v1/webhooks/channels/api/{instance}` (signed, no key) | [API channel](/docs/integration-guide/api-channel?lang=en) |

Body fields, response schemas and curl, Node.js, Go and PHP samples for every endpoint are in the [API reference](/docs/api-reference?lang=en).
