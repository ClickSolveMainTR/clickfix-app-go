# Workforce and agent development (CF-107, CF-109)

Backend APIs use the normal response envelope, JWT authentication and `X-Organization` (slug or UUID). No new environment variables or external services are needed. Routes are registered in the API server; the read-only timesheet adapter is registered in both API and worker ioengine registries.

## Forecast and staffing

`POST /v1/tenant/workforce/forecast` requires `tenant.schedules.read`. Select `channel` and/or `team_uuid` to forecast a channel/team, or omit them for the organization total. Team attribution is the conversation's current assigned team. Historical source is non-deleted conversations, not the asynchronous analytics projection. The response includes training dates, sample conversation count, timezone and effective model parameters.

The simple seasonal model trains on the last eight complete weeks (1,344 UTC hours) ending at the current complete hour. Empty hours are zero observations. Each observation belongs to the organization's local **day-of-week × hour-of-day** cell. The first observation initializes that cell; subsequent weeks update `forecast = alpha * observed + (1-alpha) * previous`, with default alpha 0.3. Each future hour reuses its cell. There is no trend or holiday adjustment. No history yields zero demand, identified by `history_conversations=0`; this is not evidence that future demand is absent. UTC hourly intervals avoid ambiguous timestamps at daylight-saving transitions; repeated local hours are separate observations of the same cell and skipped local hours produce no observation. Zones with half-hour offsets are approximated by the local hour at the UTC bucket's start.

Forecasts must start on a UTC hour at or after the current hour and no more than 90 days ahead; the horizon is at most 31 days. `granularity=day` sums hourly volume, required agent-hours, scheduled agent-hours and **positive hourly gaps**, grouped by the organization's local date. Surplus in one hour does not cancel a shortage in another.

Erlang C assumes Poisson arrivals, exponential independent handling times, one conversation per agent, an infinite waiting room and no abandonment. With hourly volume V and average handle time H seconds, offered load is A=V×H/3600. The stable Erlang-B recurrence B(n)=A×B(n−1)/(n+A×B(n−1)), B(0)=1 gives C(n)=B(n)/(1−A/n+(A/n)×B(n)) for n>A. Service level at wait T is `1-C(n)*exp(-(n-A)*T/H)`. Choose the smallest n meeting `target_sla` (default 0.8 within 30 seconds with 300-second AHT). This is an estimate, particularly for asynchronous channels and concurrent chat. These parameters are explicit inputs rather than guessed historical handling times. No shrinkage or occupancy multiplier is assumed. Calculation stops at 10,000 agents; `capacity_limited=true` means the target was not reached and the displayed number/gap is a lower bound.

Coverage uses CF-105 `agent_shifts`: distinct current members whose shift covers the **entire** hour and whose approved time off does not overlap any part of it. Team filtering uses current team memberships. Partial shifts are conservatively excluded. A channel filter changes demand only: shifts have no channel assignment, so coverage represents the selected team's entire staff and must not be summed across channel forecasts. A person on multiple teams can appear in each team's individual forecast; these forecasts must not be summed as independent staff pools.

## Activity and timesheets

`POST /v1/tenant/workforce/activity` requires `tenant.schedules.read` and records only the authenticated member. Supply a new `client_uuid` for each activity transition/heartbeat; retries return the original event and timestamp. State is `active`, `away`, `handling` or `offline`. Handling requires `conversation_uuid` and the normal inbox visibility checks. Other states cannot carry a conversation. Timestamps are server-owned, so callers cannot backdate paid time. Per-member writes are serialized. These append-only workforce activity events are the source of the timesheet; audit records and transactional `workforce.activity` outbox events accompany API mutations. Generic audit events are not interpreted as proof of agent presence.

Clients should emit state changes, an offline event on exit when possible, and heartbeats once per minute while present. An interval ends at the next activity, the report boundary, current time, or five minutes after its event, whichever comes first. This prevents a disconnected browser from accruing unlimited hours. States are mutually exclusive: handling time is reported separately from active time; use active+handling for working time. Away is separate. Reports clip intervals crossing the requested start. No integration with an unimplemented frontend heartbeat is implied by this backend delivery.

`GET /v1/tenant/workforce/timesheets` requires `tenant.schedules.manage`, accepts half-open `since`/`until` (RFC3339), optional `agent_uuid`, and groups seconds by agent, state and conversation. Maximum 31 days and 10,000 grouped rows; larger datasets return a conflict and must be split. Deleted conversations lose their public conversation identifier in reports. `/timesheets/meta` advertises read/export capability. `/timesheets/export` uses the same filters plus `format=csv|xlsx|json`, executes a bounded synchronous ioengine export as the existing contacts export does, and records an audit event. No long-lived public artifacts or extra export permissions are created. The registered adapter refuses to export without orgctx and does not support importing timesheets.

## Calibration and coaching

All calibration and coaching endpoints require `tenant.quality.manage`. Calibration additionally enforces the inbox conversation visibility policy. `POST /v1/tenant/quality/calibrations` selects a resolved conversation and a CF-108 scorecard, and snapshots the rubric. Reviewers submit `scores` to `/{uuid}/scores` using the same weighted scoring and critical-failure rule as ordinary QA. One immutable submission per authenticated reviewer prevents a reviewer from simulating multiple participants. Closed sessions reject scores. Session close and score insertion share a row lock. `/{uuid}/close` requires two distinct reviewers and is idempotent thereafter.

`GET /{uuid}` returns session metadata while open; peer scores are hidden to support independent scoring. After close it also returns reviewer results and total/per-criterion mean, population variance (sum squared deviations divided by reviewer count), range and sample count. Scores are separate from production `qa_reviews` and do not change an agent's performance KPI. Editing a scorecard does not rewrite the calibration. The list endpoint is bounded/paginated; if a page includes an inaccessible conversation it rejects that page rather than exposing its identifiers or counts.

`POST /v1/tenant/coaching` creates a note, goal or task for a current organization agent. A follow-up task requires a due date and parent goal for the same agent/organization. Notes have no due date or parent. List with `agent_uuid`, `limit`, `offset`; `PATCH /{uuid}` with `completed` completes or reopens goals/tasks. Coaching content is visible to quality managers, not the public leaderboard. Follow-up tasks are stored and listable, without an invented email scheduler.

## Gamification

`tenant.quality.manage` configures rules with `PUT /v1/tenant/gamification/rules`; upsert uses the organization's rule name. At most 100 rules, configurable name (badge), metric, threshold, points, minimum samples and enabled switch. Disable rather than delete to retain the configuration identity. The same badge is awarded **once per requested evaluation window** when its KPI passes, contributing its configured points. Evaluation is live and deterministic; repeated leaderboard requests never accumulate additional points. This implementation provides window-specific points rather than an all-time ledger, and changes to rules apply retrospectively.

KPI sources are authoritative conversation/rating records and manual CF-108 QA reviews. Resolutions count `resolved_at` in the window; first response time averages valid `first_response_at-created_at` for responses in the window (lower is better); CSAT averages scores in 0..5, based on ratings created in the window; QA averages manual scores in 0..100 created in the window (higher is better). Each rule requires `min_samples`, including resolution count, to avoid zero-data awards. Conversations/ratings use the current assignee; QA uses the review's snapshotted agent. Calibration results and automatic QA reviews do not earn points.

`GET /v1/tenant/gamification/leaderboard` requires `tenant.schedules.read`, accepts `since`, `until` (at most 366 days), optional `team_uuid`, `limit`, `offset`. Teams select current members; their KPI totals include all their work in the organization. Only current active users are ranked. Ties share competition rank, with stable UUID order within a tie. Maximum 10,000 members. `GET/PUT /preferences` reads/sets the authenticated user's own `opted_out`; opted-out members are excluded before scoring and pagination. No manager can use this endpoint to change another user's preference.
